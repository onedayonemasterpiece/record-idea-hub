# Голосовая заметка как вход в вопросы и работу над проектами

Дата анализа: 17 октября 2026. Статус: предложение для обсуждения, не внедрение и не разрешение на подписки, рассылки или изменение runtime.

## Вывод

Сделать можно без изменения Android и без универсального workflow-движка. Нужна небольшая надстройка над существующим Voice Intake и существующими question sessions Projects Hub. Базовая запись, распознавание и сохранение заканчиваются независимо от аналитики. dot выполняет содержательный аудит; backend хранит версии, очереди, полномочия и подтверждения результата.

Полная предлагаемая онтология Projects Hub для первого сценария НЕ обязательна. Обязательны её полезные границы: источник не равен решению, человек не равен его участию в конкретном событии, документ не равен Slack-сообщению, выполненная запись подтверждается фактическим readback.

Нельзя обещать абсолютную безотказность внешних сервисов. Практическая цель: заметка не теряется, повтор не создаёт дубль, незавершённая аналитика видна и возобновляется, частичный результат не выдаётся за полный.

## Уточнение владельца

Фразу «задай мне вопросы» достаточно произнести внутри самой голосовой заметки. Триггер читается из её окончательной расшифровки; отдельное сообщение, кнопка или открытие Projects Hub для запуска не требуются. Это целевое поведение надстройки, ещё не внедрённая функция.

Подкаст и лекция далее — иллюстрации и удобные приёмочные примеры, не исчерпывающий список сценариев. Процесс универсален по темам и проектам: dot определяет предмет, релевантные источники, недостающие сведения и целевые документы по содержанию. Фиксированный технический обработчик событий не означает фиксированный набор предметных сценариев.

### Ещё один существующий механизм, который нельзя продублировать

В main уже есть [ChatGPTNoteAnalysisSync](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/chatgpt_note_analysis.py) и [контракт внешнего анализа заметок](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/docs/operations/chatgpt-hourly-note-analysis.md): приватный companion Markdown, проверка source blob SHA, дедупликация по (note_id, source_sha), только включённые маршруты и заданные context refs. Аналитический результат не используется как свой исходник и сам по себе не создаёт задачи.

Это не готовый новый цикл, но его проверку source и публикацию результата следует переиспользовать/согласовать, а не запустить рядом вторую конкурирующую обработку. Существующие правила центральной Миры как semantic writer доски не отменяются: внешняя аналитика dot и разрешённые изменения документов не означают произвольную запись в доску через новый обходной путь.

## Сквозной сценарий

### 1. Сначала закончить обычную запись

Запись → распознавание → сохранённая заметка → verified publication → обычный terminal status. Android complete означает только queued, не готовый текст. Триггер аналитики нельзя ставить на этот ранний ответ.

После подтверждённой публикации запись с командой «задай мне вопросы» получает отдельный durable analysis intent. Он не меняет успешный результат записи и не удерживает её аудио ради аналитики. Сбой dot/PH/Slack означает pending аналитики, а не failed заметки.

Точное создание intent и фиксация исходного source commit должны быть устойчивы к рестарту. Предпочтительно расширить существующий ledger небольшой outbox-записью, без новой инфраструктуры очередей. Транспорт доставки работает отдельно от ASR worker; потерянные уведомления сверяются с durable intent. Для старых заметок автоматический исторический запуск по одной найденной фразе не включать без отдельного решения владельца.

### 2. Фраза запускает намерение, а не безусловные действия

Простой нормализованный поиск фразы в окончательной расшифровке может выделить кандидата. dot проверяет её смысл: «не задавай мне вопросы», цитата чужой просьбы или обсуждение самой функции не должны создавать пакет.

Нельзя запускать аналитику по частичному ASR-тексту, summary или повтору доставки. Сохраняется точное место команды и версия источника. Аутентифицированная запись владельца отличается от импортированного разговора или чужого документа: текст внутри источника сам по себе не выдаёт полномочий.

Новая скрытая модель-классификатор на backend не нужна. При явной команде dot сразу исследует контекст; уточнение нужно только при существенной неоднозначности. Наличие фразы разрешает предложенный вопросный процесс в пределах настроенного доступа, но не произвольную публикацию содержания во всех проектах.

### 3. Собрать контекст широко, но по смыслу

dot читает полную заметку, уже связанные записи и открытые раунды, затем соседние записи как кандидатов, историю нужных предметов, документы и разрешённые Slack-треды. По обнаруженным связям расширяет поиск в другие проекты. Не ограничивать всё одним текущим проектом, но и не выгружать всю историю пользователя в каждый запуск.

Каждое основание имеет ссылку и версию. В результате видны прочитанные направления и значимые недоступные источники. Непрочитанная история не выдаётся за полный аудит.

Одна запись остаётся одним intake. Несколько записей по одной теме входят в один versioned input manifest; оригиналы не склеиваются и не переписываются. Одна запись с несколькими темами может дать разные связанные направления работы с собственными адресатами.

Соседство во времени не равно общей теме. Новая запись сначала сопоставляется с существующими делами/анализами и предметами; если неоднозначность повлияет на изменения, dot спрашивает, к чему её отнести. Записи без команды допустимы как релевантный контекст, но это не запуск отдельной автоматической обработки каждой старой записи.

### 4. Вопросы и ответы

dot формирует короткий пакет существенных вопросов: что неизвестно, почему важно, какое решение зависит от ответа. Используется существующий PH question_package, не второй механизм вопросов. При большом объёме вопросы группируются по приоритету в несколько раундов, без потери оставшегося списка.

PH backend хранит пакет и receipts ответов; Мира служит голосовым интерфейсом. В заметке появляется «Вопросы от аналитика» с раундом, статусами и ссылками на ответы.

Сейчас вопросы запускаются от PH note и точного Slack binding, origin=mira/slack. Новый voice-origin требует узкого адаптера: доверенный owner, immutable source refs и разрешённые destinations. Не притворяться, что этот вход уже поддержан.

Следующий анализ запускается после явного завершения пакета, в том числе осознанно частичного. Не после каждой промежуточной реплики. Это сохраняет существующие pause/resume/important-only и не тратит повторно ресурсы на незаконченный ответ.

Если сведений не хватает, создаётся связанный следующий round с новым ID и ссылкой на прежние answer receipts. Текущий questions_ready принимает analysis_result, не новый question_package: этот переход необходимо добавить явно. Не переиспользовать старый command как новую задачу. «Не знаю», пропуск, отложенный и окончательный ответ не смешиваются; дополнительные вопросы появляются из существенных пробелов, не из требования выполнить фиксированное число циклов.

Собственные сообщения dot и обновления аналитических секций никогда не становятся новыми командами владельца. Это предотвращает цикл «результат анализа снова запустил анализ».

Новый input во время анализа отмечает необходимость следующего прохода. Для одного набора предмет/контекст не должно быть двух конкурирующих писателей. Перед сохранением выводов сравниваются версии входов. Непрерывный поток новых записей не должен бесконечно откладывать готовый пакет: фиксируется снимок раунда, новые относящиеся данные переходят в следующий. Ограничение бесконечного цикла: не повторять отвеченное, объяснять оставшийся пробел; при отсутствии новой информации оставлять понятный waiting_owner/partial, а не бесконечно генерировать вопросы.

### 5. Интегрировать, а не только написать отчёт

Когда сведений достаточно, dot составляет изменения по каждому владельцу данных: какой документ/объект, основание, ожидаемая версия, требуемое действие и получатель.

Через разрешённый API или документный gateway вносятся изменения. Каждый результат проверяется чтением. Отдельно фиксируются:
- анализ и основания;
- принятые владельцем решения;
- предложения, ещё не ставшие решениями;
- фактически изменённые документы и их версии/ссылки;
- ручные задачи и то, что не выполнено.

Глобальная транзакция между GitHub, PH и Slack не нужна. Нужны независимые подтверждения по адресатам и продолжение только незавершённых действий. Повторный запуск не переписывает уже принятые изменения и не отправляет дубли.

Slack получает краткий результат и ссылки в уже проверенный предметный тред. Успешный документ и failed Slack — частичный результат доставки, а не основание повторно менять документ. При неизвестном исходе отправки сначала прочитать тред и сопоставить сообщение.

## Минимальное состояние, без второго workflow-движка

Использовать существующий analysis/request lifecycle PH и реестр materialization IdeaHub. Добавить лишь недостающие связи:
- origin/source reference: session ID, immutable transcript hash/commit;
- input manifest: список версий связанных заметок и использованных источников;
- родитель анализа, round ID и использованные answer receipts;
- точные project/document/subject/thread destinations и их разрешения;
- результаты отдельных применений и доставок.

Это концептуальный контракт расширения, не уже существующая API-схема. Не дублировать полный case lifecycle одновременно в Record ledger, GitHub и PH: у Record остаётся источник и очередь передачи; у PH — вопросный lifecycle; у owning продукта — его факты/документы; в заметке — читаемая проекция состояния и результатов.

Новый запуск без PH backend не обязан немедленно подготовить вопросы, но обязан сохранить заметку и намерение, показать pending и продолжить позже. Независимость от открытого приложения PH достижима; полное отсутствие зависимости от PH backend для самой Миры невозможно без второго вопросного сервиса, который здесь не предлагается.

## Границы онтологии

[Онтология24 в PR172](https://github.com/onedayonemasterpiece/projects-hub/blob/751694b2eff0b36e94bb5fe2d688fd6772afa6ca/docs/product/24-ontology-from-user-stories.md), [минимальная вертикаль27](https://github.com/onedayonemasterpiece/projects-hub/blob/751694b2eff0b36e94bb5fe2d688fd6772afa6ca/docs/product/27-voice-first-mvp-vertical-20261014.md), [review25](https://github.com/onedayonemasterpiece/projects-hub/blob/4f2e32d50369b141d8a2f02752e160fe73ef422d/docs/product/25-collaboration-model-dot-review-20261014.md), [routing review26](https://github.com/onedayonemasterpiece/projects-hub/blob/4f2e32d50369b141d8a2f02752e160fe73ef422d/docs/product/26-mira-information-routing-review-20261014.md) — предложения, не подтверждённый runtime.

Совместимое соответствие:
- запись — source/evidence;
- общая тема — связанный analysis/case над конкретным предметом, не новая сущность на каждое сообщение;
- человек, лекция, выпуск — subject;
- участие человека в выпуске — отдельная связь;
- вопросы, ответы и анализ — существующие специализированные подсистемы;
- документ — каноническое место сведений либо явно обозначенная проекция;
- Slack thread — канал обсуждения предмета, не единственная база данных.

Для подкаста гонорар, тема выступления, доступность по датам и согласие относятся к участию человека в конкретном выпуске. Их нельзя записывать как вечное свойство человека. Возможная дата не равна подтверждённому расписанию; намерение выступить не равно приглашению или финансовому обязательству.

Для лекции фиксируются lecture/document/thread refs. Идея изменения сценария, заметка докладчика и задача найти визуальный материал различаются. Выполненная задача требует результата/ссылки, не только записи в Slack.

Можно заложить необязательные case_id/workflow_version для будущей миграции. Не нужно сейчас внедрять универсальный DSL/BPM, полный архив Slack, новую векторную базу, новый ASR или отдельную разговорную модель. Новый запрос добавляет приоритетный сценарий к предложенной вертикали27, а не автоматически утверждает весь отложенный объём.

## Конкретные несовместимости, которые надо закрыть

1. **Зависимость Миры от Slack.** В текущем mcp_bindings.py analysis_result сохраняет mira_state=pending; переход available и личное событие происходят после confirmed Slack receipt. Разделить сохранение результата/доступность Мире и Slack delivery. [Код](https://github.com/onedayonemasterpiece/projects-hub/blob/76bc5f2d84424f26bf3d0056687ae6a5dfcbde81/src/projects_hub/mcp_bindings.py#L345-L444).
2. **Самоинвалидация заметки.** Изменение source revision вызывает QUESTION_SOURCE_STALE. Вопросы и анализ должны обновлять управляемые секции/проекцию, не менять immutable transcript revision текущего пакета.
3. **Гонка начальной публикации.** До published_verified publisher требует byte-identical source/detail. Не вставлять аналитику в незавершённый source packet. [Publisher](https://github.com/onedayonemasterpiece/my-data-hub/blob/e7972f7339b0abe28634bd1782c0d517c65ab06e/src/my_data_hub/voice_intake_v2/publisher.py).
4. **Многократные раунды и история Git.** Reconciliation ищет исходную четырёхфайловую публикацию только в последних 10 commits source path. Использовать сохранённый исходный github_commit_sha, а не расширять произвольное окно.
5. **TTL не равен сохранности заявки.** Текущие ограничения транспорта: question_start 1 час, continuation 7 суток, subscription до 24 часов. Истечение подписки не должно терять пользовательское намерение. Нужны проверка состояния и штатное возобновление/redrive, а не предположение «webhook доставится всегда».
6. **Разные раунды.** Типизированный переход questions_ready → next round отсутствует; добавить его с version guards и сохранением ответов.
7. **Идентичность.** Record API использует configured device token; device_label не доказывает owner. Добавить серверную привязку существующего аутентифицированного устройства к владельцу, не доверять имени из расшифровки.
8. **Неизвестные маршруты.** Не делать Slack binding обязательным условием сохранения заметки или намерения. При неизвестном проекте/треде сохранить приватно pending_binding и уточнить, не создавать автоматически чужой/новый тред.

## Доступ и публикация

Чтение разрешённых проектов для анализа не равно разрешению копировать весь разговор в их документы и каналы. Действующая карта IdeaHub содержит read-доступ и не является универсальным разрешением на запись.

До автоматического применения требуется ограниченная политика владельца: какие документы можно изменять, какие изменения требуют подтверждения, в какие точные треды и какой объём данных можно отправлять. Гонорары, частные договорённости и персональные данные нельзя безусловно зеркалировать в публичный repository/общий канал.

Если текущая заметка хранится в публичном месте, приватная аналитика должна остаться в доступном только владельцу месте со ссылкой/безопасной проекцией. Политику существующего intake не менять молча. На запуске проверять фактическую видимость destination.

Подготовка этой схемы не включает настройку постоянного доступа, создание подписки или разрешение всех будущих изменений. При внедрении использовать уже выданные полномочия, запрашивая только действительно недостающие.

## Порядок реализации без церемоний

**Вертикаль 1: одна запись → вопросы → ответы → один проверенный документ.** Добавить post-publication intent, источник/owner binding и передачу в существующий question flow. Исправить Slack-зависимость и source revision projection. Проверить wake настоящего idle dot, сохранение вопросов, ответы Мире и продолжение. Завершить реальным изменением согласованного документа и отображением результата в той же заметке, не останавливаться на событии.

**Вертикаль 2: несколько связанных записей и повторные вопросы.** Versioned input manifest, связанный следующий раунд, присоединение новой записи без потери ответов и повторного применения результата.

**Вертикаль 3: несколько продуктовых документов и предметные Slack-треды.** Typed routes, минимальные проекции по аудиториям, независимые receipts и явные ручные задачи. Проверить на сценариях подкаста и лекции, не на искусственном «hello».

Все изменения backend/contracts/docs. Android, микрофон, VAD, ASR-путь и обычный режим без аналитики не меняются. Наличие unit-тестов не подменяет live-приёмку событий и фактических документов.

## Приёмка

Два предметных сценария: две отдельные голосовые про участие одного гостя в конкретном выпуске и одна голосовая про существующую лекцию. Похожая фамилия/название в другом проекте не должны перехватывать маршрут. Это дополнение к отказоустойчивости ниже, а не замена её искусственным тестовым сообщением.


| Сценарий | Требуемое наблюдение |
| --- | --- |
| Без команды | Старое сохранение/purge и число внешних запросов не меняются |
| Команда в финальной расшифровке | Один intent, один первый пакет |
| Отрицание/цитата команды | Нет нежелательных вопросов и действий |
| PH/dot/Slack недоступны | Базовая заметка доступна; pending аналитики сохранён |
| Рестарт на границах стадий | Нет потерянной заявки, повторного ASR или дубля результата |
| Повтор webhook/answer/complete | Один логический раунд; прежний результат читается повторно |
| Ответы ещё идут, пакет paused | Новая аналитика не запускается на каждую реплику |
| Нужно уточнение | Связанный второй раунд использует прежние ответы |
| Новая запись во время анализа | Сохранена новая версия контекста, нет конкурирующих изменений |
| Две темы рядом / одна тема в нескольких записях | Нет механического слияния или потери связи |
| Зеркалирование вопросов в ту же заметку | Не возникает ложный QUESTION_SOURCE_STALE |
| Документ изменён человеком | Version conflict/re-read вместо потери правок |
| Slack send с неизвестным исходом | Readback/reconciliation, не слепой повтор |
| Истекла подписка/TTL | Intent видим, штатно возобновляется, не забывается |
| Более 10 обновлений заметки | Исходная publication receipt проверяется по сохранённому commit |
| Неподходящий actor/проект/тред | Отказ без утечки и без подмены получателя |
| Подкаст и лекция | Правильные canonical документы; ссылки/версии; ручное не объявлено выполненным |

**Done:** от настоящей голосовой записи с явной командой до сохранённых вопросов, ответов, фактических продуктовых изменений и проверяемых ссылок; при отключённых зависимостях основная заметка остаётся работоспособной. Все непройденные участки перечислены отдельно. Только после такой проверки можно считать надстройку принятой.
